# 字数容量与编码器精度控制

每臂均使用同一组 39 条自然语音、自动语言、实际 FullCapture 10s/14s 分窗和真实扩展 Worker，完成 78 个片段与 115 个 Apple/Metal-3 WebGPU 窗口。78 对完整输入 PCM 与 115 对窗口边界、顺序及 PCM SHA 全部相同；全部 ready/progress=1、complete 取消与 owned browser close。[配对数据](./budget-precision-paired.json)保存逐片段指标、输入身份和三个不可变 Worker SHA。

这是 [原生产分窗矩阵](./full-capture-matrix.md)之后的独立控制：原候选 q4、统一预算 440 的 q4、预算 440 的 FP32 编码器 + q4 解码器。FP32 臂只改临时产物的 GPU dtype initializer，401 个非 Worker 文件相同。原 q4 initializer 使用字符串；实验使用分模块 mapping。实验 RPC 仍返回旧字段 dtype=q4，该字段不代表实验编码器精度。清单与缓存 SHA、实际请求的映射另行记录；FP32 没有成为产品默认值。

统一 440 对原 q4 的逐片段误差：Tiny 改善 3、相同 32、变差 4；Base 改善 3、相同 35、变差 1。Tiny 印地语 hi_in_0001 从 40/40 WER 变为 202/40，实际输出 202 个计分词，说明扩大容量同时暴露了严重异常重复。预算扩大不能被写成普遍准确率改善。

同为预算 440，FP32/q4 相对 q4 的 Tiny 结果为改善 23、相同误差 6、变差 10；Base 为改善 14、相同误差 17、变差 8。两模型共 37 改善、23 相同、18 变差，只有 8 个文字 SHA 相同。FP32 减少了 Tiny 印地语的异常长度，但 Base 印地语、阿拉伯语等仍有明显错误，不能只据多数片段改善切换默认精度。
