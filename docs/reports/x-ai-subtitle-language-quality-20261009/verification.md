# X AI 字幕：多语种与识别质量

用户常看的视频包含无法预先指定的多种语言。本轮加入实际 Whisper Small 模型，推荐自动检测，并修复语言锁定、长视频分窗和慢设备等待问题。新配置推荐 Small（约 590 MB，FP32 编码器、q4 解码器），已有 Tiny/Base 选择继续保留。手动指定源语言仍为可选设置。

## 已确认的问题与实现

- 原 Worker 在同一流中检测到两段足够长且高置信度的相同语言后永久锁定语言。后续语言变化不再执行检测。现在每个有声窗口重新检测，语言概率只描述当前窗口。
- 自动检测和生成原本分别编码同一段音频。锁定 Transformers.js 3.8.1 的单实例适配现在共用一个编码张量，并继续使用库的原有生成、timestamp 和文本后处理。实例配置在 finally 恢复，张量在请求结束后释放；不兼容接口使用原检测路径。Mel 预处理仍执行两次，不能宣称整条预处理只执行一次。
- 原完整捕获会在首窗识别完成前复制整片的所有识别窗。现在只有一个活动窗和一个预备窗；保留 20 分钟上限、原分窗位置、重叠和有声尾窗规则，在窗口间让出页面任务。
- 消息响应保留当前窗口的实际检测语言、概率、检测时间和编码复用状态。`inferenceMs` 从检测前开始计时；显式语言不伪造检测结果。旧版该字段不包含检测成本，跨版本耗时比较使用完整 RPC 或相同驱动的 wall time。
- Tiny 保留原有输出预算，Base/Small 使用 440 个生成 token；包含三个 prompt token 后为 443，低于模型的 448 上限。字幕策略缓存升级为 `video-ai-cues-v2`，避免直接恢复旧策略产生的字幕，模型下载缓存继续复用。
- 首次准备成功后，模型最多保持 90 秒等待首窗，后续空闲保留 30 秒。同一持有者反复准备不能续期；完成、取消和失败会清理。停止操作立即取消，晚到结果不能写回字幕。
- Small 的生成、独立 Worker 和后台请求分别使用 60/180/200 秒预算，Worker 首次尝试最多 90 秒，剩余时间留给已有 WASM 恢复。视频结束后只有尚未完成的 Small 识别允许等待较长尾窗；用户停止仍立即生效。
- Small 下载总预算 600 秒，单文件来源 300 秒，保留 20 秒无数据超时；只允许其已知 FP32 编码器达到 384 MiB，其他模型文件仍限 256 MiB。预下载按七文件清单全部完成后登记，并检查不完整传输和实际字节数；暖准备另以实际 Worker 初始化成功为依据。

## 定向模型与分配证据

真实 Node-hosted ORT Web WASM 执行生产 Worker 的 dispatcher、检测、生成和后处理，仅替换本地资源加载和 Worker 消息边界。Transformers.js 3.8.1、ORT Web 1.23.2、单线程、q4 默认 optimizer；这是模型执行证据，尚不等于浏览器或实时 X 的验收。

8 组 Tiny/Base 配对输入的编码 session.run 次数从 2 次变为 1 次，decoder 次数、完整文字与所有 segments 完全一致，processor 仍为 2 次。同一流的英文、英文、普通话序列，旧版第三窗跳过检测，新版实际检测为 `en/en/zh`，普通话输出恢复为独立自动检测的相同 SHA。第三窗的有限合成普通话 CER 从 36/15 降到 5/15，仍有错误。合计 22 次实际 ASR 调用完成。

每组单次 Node wall 观察下降 25.6%–34.8%，不能作为所有设备或稳态单语窗口的速度结论：旧版确认语言后的窗口原本只编码一次，新版逐窗检测有额外 SOT 和 Mel 成本，需另行测量。

20 分钟连续合成 PCM、首窗模拟识别挂起的分配反例中，原 Tiny 137 窗/87,244,800 字节与 Base 94 窗/83,942,400 字节副本，变为两窗/1,280,000 与 1,792,000 字节。完整运行逐窗核对 range、sequence 与 PCM SHA，最终仍有原来的全部 137/94 窗。76,800,000 字节源音频、模型、浏览器及原生解码内存另计；这不是总内存或浏览器速度测量。

## 自然语料与计分方法

使用 [Google FLEURS](https://huggingface.co/datasets/google/fleurs) 的公开真人朗读语音，以及发布方 [FluidInference/fleurs-full](https://huggingface.co/datasets/FluidInference/fleurs-full/blob/1cca811bb8ea4d370345f108f00518167040282c/README.md) 的逐文件测试集提取；两者标注 CC-BY-4.0。固定修订 `1cca811bb8ea4d370345f108f00518167040282c`，每个所选 locale 取编号最前的三条，不按识别效果筛选。

语料包括普通话、英文、日文、韩文、西班牙文、法文、德文、阿拉伯文、印地文、俄文、越南文、泰文与葡萄牙文，39 条，总计 467.64 秒，单条 7.2–23.4 秒。每条源文件、转换后 PCM16、参考文本和参考文件都有 SHA。音频与参考全文只保存在任务临时目录，仓库保存来源与摘要。

Tiny/Base 的显式语言与自动模式分别执行，最终 Small 验收全部使用自动模式。报告区分 cache 准备、ONNX session 准备、检测、完整推理和 RPC 耗时；独立窗口与同流语言切换分组单列。直接 Worker 的 30 秒输入边界与产品完整模式的 10/14 秒分窗不同，长样本的直接识别不能替代整片字幕验收。拼接自然单语片段用于受控语言切换，不称作自然 code-switch。

## 浏览器和播放器对照

[独立窗口对照](direct-worker-matrix.md)包含旧版与候选版各 156 次真实 Chrome WebGPU/q4 推理，自动与显式源语言分开。156 对文字 SHA 与错误分数完全一致；共享编码保持文字结果，不能称为普遍准确率提升。78 次自动检测均识别出该独立样本的标签，仍不能推断任何视频的语言检测成功率。

44.16 秒受控 X 播放器使用三个自然英语片段和一个自然普通话片段拼接后的 AAC/MP4，从实际媒体恢复、原生音频解码、完整模式分窗、真实模型到字幕显示。旧版和候选版实际送入 Worker 的四窗 PCM SHA 完全相同。旧版结尾沿用英文，修复后的 Base 检测 `en/en/en/zh` 并生成中文字幕；原始混合 CER 从 71/346（20.5%）到 30/346（8.7%）。见 [Base 精简配对](full-player-paired.json)。

最终不可变构建使用实际 Small 模型 ID、FP32 编码器和 q4 解码器重复整条播放器链路，15 项检查通过。四窗 PCM 与旧版逐一相同，实际检测仍为 `en/en/en/zh`，原始混合 CER 为 14/346（4.0%），共生成五条字幕，仍有识别错误。三模型选择提示、缓存准备、媒体恢复、实际字幕缓存和中文字幕显示均经过浏览器验证。见 [最终播放器摘要](final-full-player.json)、[模型选择截图](final-three-model-prompt.png)和[结尾中文字幕截图](final-mandarin-tail.png)。翻译响应为模拟，本证据不代表实际翻译服务或认证 X 信息流。

整片分窗语料的旧版与候选版各 78 次控制器运行完成，各调用真实 Worker 115 窗，无 RPC 失败。所有窗 PCM、最终文字 SHA 与错误分数相同，9 个低置信度尾窗的检测标签与整条语音标签不一致，且旧版文字也相同；这表明原有尾窗识别弱点仍在。控制页注入本地 PCM，不能代替播放器取音或 UI 验证。

## 输出预算与模型精度决策

锁定相同的 Whisper tokenizer，对 39 条参考文本计算正常 BPE 数和任意合法字节 token 分词的最短下界。短于产品窗的泰语、印地语和部分阿拉伯语参考，在旧预算中无法容纳正文，更无法再容纳 timestamp/EOS。9.12 秒印地语至少需 119 个正文 token，Tiny/Base 只给 55/64；13.8 秒印地语至少需 199，Base 只给 96。三条泰语分别至少需 101、65、133，而 Base 只给 62、51、67。详见 [预算审计](token-budget-audit.json)。这与量化造成的字词误识别分别验证。

输出预算 440 的第一轮完整模式对照已完成，78/78 无 RPC 失败，但存在真实质量回归：Tiny 印地语 WER 的错误数从 107/93 增到 269/93，泰语 CER 从 279/355 增到 340/355；Base 泰语从 256/355 降到 161/355，印地语从 94/93 到 96/93。容量缺口成立，单独提高上限仍不足以改善所有语言；该实验不得描述为统一提准。

因此最终恢复 Tiny 原预算，不统一切换 Tiny/Base 编码器精度；Base/Small 保留 440。FP32 编码器与 q8 解码器的独立控制详见[精度对照](budget-precision-controls.md)和[解码器诊断](decoder-text-diagnostic.md)，它们没有解决所有语言的误识别。

Small 的探索性模型别名对照仅用于选型，详见[模型控制](small-model-controls.md)；它不能代替实际产品 Small ID 的验收。最终正式模型的 39 条、48 窗自动识别均成功，摘要与逐条配对见[最终 Small 矩阵](final-small-model-matrix.md)。

只读检查发现 Transformers.js 3.8.1 的 Whisper.generate 丢弃传入的 stopping_criteria，原计时标志只能在生成结束后拒绝结果，offscreen 的独立硬超时仍有效。现在请求期间在当前模型实例注入原有 criteria hook，显式、自动和编码复用路径均覆盖；finally 恢复原属性。真实锁定库的[零推理契约](stopping-adapter-contract.json)核对保留 MaxLength/EOS 且实际 InterruptableStoppingCriteria 可使返回条件从 false 变 true。该证据不等于实测 ONNX 每次在预算边界精确停止。

实际 Small 的两条印地语 Node-hosted ORT Web WASM 控制分别耗时 40.02/76.55 秒，其中检测 14.43/24.69 秒，WER 为 14/24、29/40。进程最大 RSS 约 3.11 GB，不是浏览器内存测量。此控制执行的是最终超时调整前的生产 Worker，来源 SHA 保存在[WASM 控制](small-wasm-control.json)；同线程 WASM 可阻塞定时回调，因此不能用其完成结果证明 15 秒停止有效。这也是最终为 Small 单独延长预算、保留独立线程硬超时的依据。

## 模型能力与计分边界

[参考文字审计](reference-normalization.json)确认 39 条参考均为 NFC，印地语和阿拉伯语参考的 NFC/NFKC 不改变字形。实际取回的受控输出还存在印地语自动检测后生成大量拉丁或阿拉伯文字的情况，不能把高错误率完全归于 Unicode 规范化。原始文字仅在本机任务临时目录诊断。

[OpenAI Whisper 论文](https://cdn.openai.com/papers/whisper.pdf) Table 13 的 Tiny/Base/Small 印地语 WER 为 102.3/101.1/38.4%。这是原模型与上游计分、解码设置下的整体基准；Appendix C 会改变非英语结合标记处理，不能直接对比当前小样本错误率。它支持评估更强的多语种模型，不能代替当前浏览器 Small 验证。

最终浏览器样本的印地语仍为 76/93（81.7% WER），泰语为 96/355（27.0% CER）。Small 有较高下载、内存和 CPU 成本，普通设备可能等待较久。本轮不能声称所有 X 视频可用、所有语言达到优秀准确率，或 q8 在 GPU 上普遍更快、更准。实际 X 账号、线上翻译服务、Firefox 真实推理和更多设备仍需分别验收。
