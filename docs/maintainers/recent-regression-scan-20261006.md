## 扫描与验证结果

人工检查集中于图片识别/显示、配置默认值和保存、条件云同步、下载取消与进度、相同译文的显示例外、局部选择生命周期、词书、语音与视频媒体身份。自动测试覆盖近期改动与全部架构契约；这不等于逐行审阅所有 838 个文件，也不保证不存在其他缺陷。

- 157 个测试文件：156 个通过，1 个失败；4492 个用例中 4491 个通过。
- 唯一失败是 `verificationOwnership` 中 18 个既有模块缺少严格覆盖登记。在不含本次改动的 `190a96e6` 临时源码快照上单独运行同一审计，得到完全相同的 18 个路径。本次没有增加这项缺口，未豁免或修改该门禁。
- 本次修改的 `presentation.ts` 和 `mangaOcr.ts` 经 227 个针对性用例验证，statements、branches、functions、lines 均为 100%。
- 修复过时的输入框翻译默认服务、合并后的图片设置位置、拆分后的语音/字幕组件、WASM 初始化包装与划词滚轮契约断言；图片跨域安全用例补齐 Node 环境的浏览器 API 注入，保留真实消息封装。
- 测试分类审计通过：481 个文件、6501 个登记用例。登记数量不是实际执行数量。
- TypeScript/Vue 编译、Chrome MV3、Firefox MV2、扩展 manifest 核验、油猴构建和油猴产物 verifier、文档构建通过。

## 同日补查：登录后 X 的透明原图

用户使用 PR #869 的修复构建后仍看不到入口。对其提供的现有帖子只读检查发现，登录后的 X 与匿名页面使用不同的图片结构：透明 `img` 接收鼠标，同级、同源且同尺寸的背景层绘制图片。遮挡检测把这张原 `img` 当作外部前景，隐藏了整个图片操作层。初次验证没有覆盖这个结构，不能代表登录后的 X 已修复。

现在 runtime 将原图身份传入遮挡检测，只接受该原图与已认领背景面的同源、同级、同尺寸对应关系，并要求原图透明度为零。背景由译图租约隐藏时仍保留原图身份；其他图片、不同来源、尺寸变化和真正的弹窗继续执行遮挡保护。保留 24×24 淡色小图标与点击区域、28% 透明度，鼠标移到图标上才恢复清晰显示；按用户反馈去掉空闲图标外层的额外留白、边框与底色，操作条由 30×30 缩至 24×24，未添加文字或放大入口。

- 两个新增用例在旧代码上分别复现遮挡误判和操作层 `display:none`；修复后相关三个测试文件的 250 个用例通过，`presentation.ts` 与既有 `controls.ts` 四维覆盖率均为 100%。
- 生产 Chrome 构建的普通图片、透明原 img、inert 透明链接与原生按钮四种夹具通过。检查实际图标解码、24×24 原有样式、鼠标命中、移出收起、图标悬浮变清晰、弹窗开关与可信点击。点击进入首次语言包准备提示，未下载模型或请求在线翻译；宿主媒体结构及链接地址保持原样。
- 实际匿名帖子及引用的前两张图片通过同样的入口检查，见 [实际帖子](./assets/x-image-hover-followup-20261006/live.png) 与 [透明原 img 夹具](./assets/x-image-hover-followup-20261006/source-img.png)。匿名回复区的登录遮罩仍是站点限制，未列入通过范围。登录账号只用于只读结构诊断，未在日常页面加载测试或执行交互。
- 测试分类审计（481 文件、6504 登记用例）、类型检查、Chrome/Firefox 构建、manifest 核验和文档构建通过。浏览器验证继续使用临时配置与第二屏后台正常窗口，`browserFrontmost:false`。
